# Практична робота №5 — MPA та SPA

## Тема
Дослідження архітектурних стратегій рендерингу веб-додатків: порівняльний аналіз MPA та проєктування SPA-інтерфейсів.

## Опис
FlowSpace — демонстраційний односторінковий вебзастосунок, створений на HTML5, CSS3 та Vanilla JavaScript (ES6+). Застосунок має три секції, хеш-маршрутизацію, глобальний таймер і локальну форму зворотного зв'язку.

## Структура проєкту
- `index.html` — семантична HTML-структура та три секції.
- `style.css` — оформлення, адаптивність і приховування неактивних секцій.
- `script.js` — таймер, маршрутизація та обробка форми.

## Запуск
1. Завантажте або розпакуйте проєкт.
2. Відкрийте `index.html` у сучасному браузері.
3. Перемикайте розділи через навігаційне меню.
4. Переконайтеся, що таймер продовжує відлік.

Сервер і база даних для демонстрації не потрібні. Для публікації на GitHub Pages можна завантажити три файли репозиторію та увімкнути Pages для гілки `main`, папки `/ (root)`.

## Перевірка через DevTools
1. Натисніть `F12` і відкрийте вкладку **Network**.
2. Увімкніть фільтр **Doc**.
3. Перезавантажте сторінку один раз — з'явиться початковий запит документа.
4. Перемикайте «Огляд», «Про проєкт» і «Зворотний зв'язок».
5. Переконайтеся, що нові запити типу `Doc` для кожного переходу не створюються. Зміна фрагмента URL (`#catalog`, `#details`, `#feedback`) не є запитом нового HTML-документа.

## Контрольні запитання та відповіді

### 1. У чому полягає фундаментальна відмінність життєвого циклу сторінки в MPA порівняно зі SPA?
У MPA перехід між сторінками зазвичай виконує запит до сервера та завантажує новий HTML-документ. Поточний документ знищується, а JavaScript-контекст створюється заново. У SPA базовий документ залишається завантаженим, а JavaScript програмно змінює видимий вміст. Тому глобальний стан може зберігатися між переходами.

### 2. Які зміни фіксуються у вкладці Network під час клієнтської маршрутизації SPA порівняно з переходом між окремими HTML-файлами?
Під час переходів у цьому SPA URL змінюється через фрагмент після символу `#`, але новий запит типу `Doc` не створюється. У MPA перехід на іншу HTML-сторінку спричиняє новий запит документа. Інші запити ресурсів можуть виникати залежно від реалізації, але в цій роботі навігація не завантажує нові HTML-сторінки.

### 3. Чому глобальний стан JavaScript руйнується при навігації в MPA?
Тому що браузер переходить до нового документа: попередній JavaScript-контекст і його глобальні змінні знищуються. Таймери, обробники подій та незбережені дані в пам'яті старого документа припиняють існування. Для збереження даних між документами потрібні окремі механізми, наприклад `localStorage`, cookies або серверне сховище.

### 4. Які переваги та обмеження має чистий клієнтський SPA порівняно з SSR та SSG щодо первинного завантаження та SEO?
SPA може забезпечувати швидкі переходи після початкового завантаження, оскільки не потребує повного перезавантаження документа. Однак перше завантаження може бути повільнішим через необхідність завантажити JavaScript, а пошуковим системам іноді складніше індексувати контент, який формується лише на клієнті. SSR повертає вже сформований HTML із сервера, а SSG заздалегідь генерує HTML-файли. Ці підходи часто покращують швидкість відображення першого вмісту та SEO, але потребують додаткової інфраструктури або етапу збірки.

### 5. Поясніть сутність процесу гідратації (Hydration), характерного для SSR.
Гідратація — це процес, під час якого JavaScript на клієнті під'єднує обробники подій і логіку до HTML, який сервер уже сформував та надіслав браузеру. У результаті статично відображена сторінка стає інтерактивною без необхідності повністю створювати її розмітку повторно.

## Висновок
Під час виконання практичної роботи було досліджено відмінності архітектур MPA та SPA. Створено односторінковий вебзастосунок із трьома секціями, реалізовано клієнтську хеш-маршрутизацію засобами Vanilla JavaScript, індикацію активного пункту меню та глобальний таймер, який не переривається під час навігації. Також реалізовано локальну обробку форми та описано методику перевірки мережевої поведінки через DevTools Network. Мету практичної роботи досягнуто.
